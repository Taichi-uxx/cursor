# Knowledge Import

他形式のナレッジを構造化mdに変換し、`~/.cursor/work/` または `~/.cursor/contents/` 配下の最適フォルダに格納するスキル。

## 入力ソース

以下のいずれか（複数同時も可）。
- 記事URL（Webページ）
- X（Twitter）投稿URL
- PDFファイル（ローカルパス）
- 文書ファイル（.md / .txt / .docx など）
- 画像やスクショ（OCR的に読み取り）
- 文章を直接ペースト

## 実行フロー

```
- [ ] Step 1: ソースを読み込む
- [ ] Step 2: 日付（yymm）を特定する
- [ ] Step 3: 内容に応じた構造でmd化する
- [ ] Step 4: 格納先フォルダを判定する
- [ ] Step 5: ファイルを作成して通知する
```

### Step 1: ソースを読み込む

- URL → `WebFetch` で本文取得。X投稿はツイート本文・スレッドを含めて拾う
- PDF → `Read` ツールで読み込み（10ページ超は `pages` 指定）
- ローカルファイル → `Read` で読み込み
- 画像 → `Read` で読み込んで内容を抽出

複数ソースが提示されたら、それぞれ独立に処理するか、1つの統合ナレッジにまとめるかをユーザーに確認する。

### Step 2: 日付（yymm）を特定する

ファイル名 `yymm_〇〇.md` の `yymm` は **そのナレッジが作成・投稿されたタイミング**。md作成日ではない。

判定優先順位：
1. URLや本文に明示された投稿日・公開日（例: 「2025年9月10日」「Sep 10, 2025」）
2. X投稿のタイムスタンプ
3. PDFのメタデータや本文中の発行日
4. ファイル名や見出しに含まれる日付

**特定できない場合は、推測せず必ずユーザーに確認する。** 例：

> 「このナレッジが作成・投稿されたタイミングを教えてください（例: 2025年9月 → `2509`）。不明な場合は『不明』と答えてもOKです。」

ユーザーが「不明」と答えた場合のみ、日付プレフィックスを省略して `〇〇.md` というファイル名にする。

### Step 3: 内容に応じた構造でmd化する

**テンプレートは固定しない。** 内容に応じてAIが最適な構造を組み立てる。ただし以下は必須。

#### 必須要素

1. **タイトル（H1）** — ナレッジを一目で表す名前
2. **出典（Source）** — URL・著者・投稿日など。後から検証できるように
3. **用途（どんな時に活用できるか）** — H2セクションとして必ず入れる。
   - 課題ベースで参照しやすいよう、「こういう場面で困ったら見る」が想像できる粒度で書く
   - 例：「クライアントへのCPA改善提案で、入札戦略の選択肢を整理したいとき」「広告クリエイティブの構成案を考えるとき」
4. **本文** — 内容に応じてAIが最適な見出し構成を決める（概要 / 要点 / 詳細 / 事例 / 学び など）

#### 構造判断のヒント

- 短い投稿・要点メモ → 箇条書き中心でコンパクトに
- 長文記事 → 概要 → 章立て → まとめ の階層構造
- ハウツー系 → 手順をチェックリスト化
- 事例紹介 → 背景 → 課題 → 施策 → 結果 → 学び
- 数値データを含む → 表で整理し「So What」を明示

#### 表現ルール

- 日本語で記述する
- 元ソースの引用と、太一の解釈・示唆を区別する（引用は `>` ブロック、示唆は通常本文）
- 冗長な前置きや一般論は削ぎ落とし、戦略家として「次のアクションが見える」粒度にまとめる

### Step 4: 格納先フォルダを判定する

現在のフォルダ構造（参考）：

```
~/.cursor/work/
├── AI活用/              ← AI・LLM・Cursor・Claudeなどのナレッジ
│   ├── 自動化PJT/
│   ├── n8n活用・ワークフロー構築/
│   ├── 分析自動化/
│   └── 具体業務での活用/
├── CS/                  ← カスタマーサクセス全般
│   ├── ENSOR/           ← 案件特化（ENSOR）
│   ├── ワークフロー/
│   ├── ファシリテーション/
│   ├── CS・Sales基礎/
│   └── マネジメント/
├── client/              ← クライアント別案件
│   ├── green/ yuzen/ hr/ jin/ zeal/
├── マーケ/              ← マーケティング戦略・施策
│   ├── toB/ モール/ クリエイティブ/ LP/ LLMO/
├── 広告/                ← 媒体別広告運用ナレッジ
│   ├── Meta/ Search/ Shopping/ Dynamic/ TikTok/ P-MAX/
├── 経営/                ← 経営・組織・事業
├── 個人/                ← 個人の振り返り・docs
├── よく使う指示/        ← プロンプト・指示テンプレ
└── _mockup/             ← UI/LPモックアップ系

~/.cursor/contents/
├── SNS/                 ← 発信用
│   ├── YouTube/ LINE/ TikTok/ Instagram/
└── 動画/                ← 動画制作素材・企画
```

判定ロジック：
1. 内容のテーマを把握する（広告運用 / AI / CS / マーケ / 経営 / 発信 など）
2. 最適なフォルダを1つ選ぶ。第2階層まで掘れる場合は掘る
3. **既存フォルダで最適なものが見つからなければ、新規フォルダを作成する**（命名は既存に揃える）
4. 業務系（work/）か発信系（contents/）かは、CLAUDE.mdの「現在=work / 未来=contents」の区分に従う

迷う場合のみユーザーに確認。明確に判定できるなら確認なしで進めてよい。

### Step 5: ファイルを作成して通知する

1. 格納先フォルダが存在しなければ `mkdir -p` で作成
2. `Write` ツールでmdファイルを作成
3. 作成完了をユーザーに通知。以下を含める：
   - 作成したファイルのフルパス
   - 格納先フォルダ（新規作成した場合はその旨を明記）
   - ファイルの構造サマリ（H1とH2の見出し一覧）

通知例：
```
✅ ナレッジを保存しました

📁 /Users/apple/.cursor/work/広告/Meta/2509_AdvantageCampaignBudget活用法.md
📂 既存フォルダ: work/広告/Meta/
🏗 構造: タイトル / 出典 / 用途 / 概要 / 実装手順 / 注意点
```

## 重要な注意点

- **日付不明時は必ず確認する**。推測で `yymm` を埋めない
- **重複チェック**: 同じテーマのファイルが既存にないか、格納前に `ls` で確認。あれば追記 or 統合をユーザーに提案
- **.env関連のファイルは絶対に扱わない**（CLAUDE.mdルール）
- **不可逆操作（上書き）は事前確認**。同名ファイル存在時は確認必須
