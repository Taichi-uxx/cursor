# LLMO（Large Language Model Optimization） — 鉄則・勝ち筋・負け筋

## 1. このドメインの本質

LLMOは **「ユーザーがChatGPT・Claude・Perplexity・Geminiなどの生成AIに質問した際、自社情報がAIの回答内で引用・推奨される確率を最大化する活動」**。
従来のSEOが **「検索結果10位以内に入ること」** を目標としたのに対し、LLMOは **「AIの脳内コンテキストに自社情報が組み込まれ、かつ回答時に引用されること」** を目指す。検索の入口がGoogle青リンクから「AIの一行回答」に移行しつつある今、**SEOの代替ではなく上位互換として向き合う必要がある新興領域**。

この本質を分解すると、LLMOは4つの構造ゲームの重ね合わせで成立している。

### 本質① LLMの「学習元」と「リアルタイム参照元」の二重構造ゲーム
LLMOは2つの異なる回路で勝負する必要がある。①**学習データ回路**：LLMが訓練時に取り込んだコーパス（Common Crawl等）に自社情報が含まれているか。これは事後追加が極めて難しい。②**リアルタイム参照回路**：ユーザー質問時にLLMがWeb検索する際に引用されるか（Perplexity、ChatGPT search、Claude search）。
**SEOで上位 ≒ リアルタイム参照で引用されやすい**、という相関はあるが等価ではない。**両方の回路を狙う設計**が必要で、Web検索引用が短期、学習データへの混入が中長期の勝負どころ。

### 本質② 「引用されやすい構造」 = AIが理解しやすい構造ゲーム
LLMは長文の中から「**質問への直接的回答**」を抽出して引用する。
つまり、見出しに「なぜ◯◯なのか」、本文に「結論：〜だから」「3つの理由：①〜②〜③〜」のような **構造化された Q&A 形式・箇条書き・明示的な結論** を含むコンテンツが圧倒的に引用されやすい。ふわっとしたエッセイ調の記事は、SEOでは上位でもLLMの引用対象にならない。**「人間に分かりやすい」と「LLMに抽出されやすい」は別軸の最適化**。

### 本質③ ブランド・エンティティとしての「文脈位置」獲得ゲーム
LLMは固有名詞を「文脈の中の位置」で理解する。「日本のSaaS人事ツール」と問われたとき、SmartHR・freee人事労務・カオナビ等が想起される——これは **LLMの学習データ中で、それらの社名が「日本」「SaaS」「人事」と共起する文脈で大量に出現したから**。
新興企業や認知度の低いブランドが LLMO で勝つには、**カテゴリ語との共起回数を増やす施策**——PR露出、業界記事への登場、Wikipedia整備、Quora/Reddit的Q&Aサイトでの言及——が効く。**「キーワードでの順位」ではなく「文脈内ポジショニング」を取りに行く**。

### 本質④ ハルシネーション・誤情報訂正ゲーム
LLMは時に **自社についての誤情報を堂々と回答する**。「A社のサービスは月額〇〇円から」「A社はB機能を提供している」——実は事実と違うのに、それが「真実」として流通する。
LLMOには **「正しい情報をLLMに認識させる積極的施策」** と **「誤情報を訂正する受動的施策」** の両方が必要。公式サイトの構造化データ整備、Q&Aページ充実、Schema.org markup、prompt injection等への対策。**自社の情報が「正しい形でLLMに届く」状態を維持する継続活動**として捉える。

## 2. 鉄則（破ってはいけない）

> 表記凡例: 各項目末尾の **〈本質①〜④〉** は、その鉄則がどの本質に紐づくかを示す。

1. **SEOを捨てない（LLMOの土台はSEO）** — Web検索引用回路では、SEO上位＝引用候補。SEO投資を維持しつつLLMO上乗せが正解。〈本質①: リアルタイム参照回路はSEO基盤の上で動く〉

2. **コンテンツは「結論→根拠→具体例」のピラミッド構造で書く** — ふわっとしたエッセイは引用されない。冒頭3行で結論、続いて理由列挙、最後に具体例。〈本質②: LLMが抽出しやすい構造〉

3. **公式サイトに FAQ／Q&A ページを必ず整備する** — 自社についての質問にLLMが答える際の参照ソースになる。Schema.org の FAQPage markup も併用。〈本質②④: 構造化＋情報供給〉

4. **業界カテゴリ語との共起を意図的に増やす** — 業界メディア寄稿／PR記事／インタビュー記事で「カテゴリ名 × 自社名」の言及回数を蓄積。〈本質③: 文脈内ポジショニングの源泉〉

5. **Wikipedia・Wikidata・主要レビューサイトの自社情報を整備する** — LLMの学習データに高確率で含まれる権威性の高いソース。〈本質①③: 学習データ回路と文脈位置の同時獲得〉

6. **誤情報・ハルシネーションを月次でチェック** — 主要LLMで自社名・商品名を検索し、誤回答があれば公式情報で訂正発信。〈本質④: 受動的訂正の継続〉

7. **E-E-A-T（経験・専門性・権威性・信頼性）を保つ** — LLMはGoogleと同様、権威ある情報源を優先引用する。著者情報・実体験・引用元の明示が効く。〈本質②③: 引用されるための信頼スコア〉

## 3. 勝ち筋（再現性のある勝ちパターン）

### 勝ち筋A: 「カテゴリ × 比較記事」の網羅展開
- **場面**: 自社サービスのカテゴリ認知獲得期
- **内容**: 「◯◯ツール おすすめ」「◯◯ サービス 比較」「◯◯ 選び方」など、カテゴリ語＋比較インテントのキーワードで、自社含む比較記事を整備（自社オウンドメディア＋外部メディア掲載）
- **なぜ勝てるか**: 〈本質①②③〉LLMはユーザー質問「◯◯のおすすめは？」に対し、Web検索→比較記事を読む→そこに記載されている社名を回答する流れ。比較記事に「載っている」ことがLLM引用の必要条件。

### 勝ち筋B: FAQ／Q&Aページの徹底整備
- **内容**: 「◯◯とは」「◯◯の使い方」「◯◯ 料金」「◯◯ 評判」など、ユーザーがLLMに聞きそうな質問を全部FAQ化。Schema.org のFAQPage markupも実装
- **なぜ勝てるか**: 〈本質②④〉LLMはQ&A構造を強く好む。質問文と回答文がペアで明示されていると、引用素材として最適。さらに自社サイトが正しい情報源になるのでハルシネーション防止にもなる。

### 勝ち筋C: 「専門家インタビュー × 一次情報」記事
- **内容**: 自社の代表・専門家による独自見解、独自データ調査、業界レポートを公開。他社が引用したくなる「一次情報」を持つ
- **なぜ勝てるか**: 〈本質①③〉LLMもユーザーも「一次情報」を優先する。引用されるソースになれば、他メディアでの言及が増え→共起回数が増え→LLMの学習・参照両回路で有利になる正のループ。

### 勝ち筋D: Wikipedia/Wikidata整備 × 業界メディア露出
- **内容**: Wikipediaに自社・代表者・主要サービスの記事を立てる（中立的に）。並行して業界メディア・PRリリース・受賞情報を出し続ける
- **なぜ勝てるか**: 〈本質①③〉Wikipediaは多くのLLMの学習データに含まれる。さらに業界メディア露出は学習・参照両方で効く。「権威ある第三者の言及」の蓄積がLLMOの中長期資産。

### 勝ち筋E: 月次のハルシネーション監視 × 訂正発信
- **内容**: 主要LLM（ChatGPT/Claude/Perplexity/Gemini）で自社関連クエリを月次でテスト。誤情報を発見したら、公式サイト・PR・SNSで正確情報を発信
- **なぜ勝てるか**: 〈本質④〉誤情報を放置するとそれが定説化する。能動的訂正で「正しい情報の流通量」を増やすと、リアルタイム参照回路で正確な回答が返るようになる。長期で見るとブランド毀損リスクを下げる。

## 4. 負け筋（典型的な失敗・地雷）

### 負け筋A: SEOを軽視してLLMO単独で動こうとする
- **症状**: コンテンツを大量生産してもLLM引用されない
- **原因**: 〈本質①〉LLMのWeb検索参照は基本的にSEO上位を辿る。SEO基盤がないとリアルタイム参照回路で勝負にならない。
- **回避策**: SEO投資を維持しつつLLMO最適化を上乗せ。両者は競合ではなく相補

### 負け筋B: エッセイ調・ふわっとした文章
- **症状**: PV はあるがLLMに引用されない、被リンクも増えない
- **原因**: 〈本質②〉結論が曖昧／構造化されていない文章はLLMが抽出できない。「読み物」としては良くても「引用素材」として弱い。
- **回避策**: 冒頭3行で結論、見出しに「なぜ／どうやって」、箇条書きを多用

### 負け筋C: 自社サイトのFAQ／構造化データ未整備
- **症状**: 自社についての質問に競合や誤情報が回答される
- **原因**: 〈本質②④〉LLMが参照すべき公式情報源が機能していない。
- **回避策**: FAQページ整備＋Schema.org FAQPage / Organization / Product markup を実装

### 負け筋D: カテゴリ語との共起ゼロのまま社名連呼
- **症状**: 自社名検索では出るが、カテゴリ検索（「◯◯ツール おすすめ」）で出ない
- **原因**: 〈本質③〉LLMの学習・参照データに「カテゴリ名 × 自社名」の共起がない。指名検索でしか勝てない狭い土俵に閉じ込められる。
- **回避策**: 業界比較記事・カテゴリレビュー・業界メディア寄稿で共起を作る

### 負け筋E: 誤情報を放置
- **症状**: LLMが古い料金・存在しない機能・代表者誤認情報を回答し続ける
- **原因**: 〈本質④〉監視も訂正発信もしていないため、ハルシネーションが定着。
- **回避策**: 月次LLMチェック＋公式情報の積極発信を制度化

### 負け筋F: AI生成コンテンツの大量量産
- **症状**: 大量のAI生成記事を公開→検索順位が下がる→LLMにも引用されない
- **原因**: 〈本質②③〉一次情報・独自見解のないAI生成コンテンツは、E-E-A-Tで評価されず、LLM側でも「他と同じ平凡な情報」として無視される。
- **回避策**: AIは下書き補助に使い、最終的に一次情報・独自見解・実例を必ず人間が追加

## 5. 判断分岐（迷ったときの基準）

| 状況 | 取るべきアクション | 紐づく本質 |
|---|---|---|
| LLMO を始めたい | まずSEO基盤の健全性とFAQ整備を優先 | ①②土台が必要 |
| 自社名検索でLLM回答が不正確 | FAQ整備＋公式情報訂正発信 | ②④誤情報訂正 |
| カテゴリ検索で出てこない | 比較記事・業界メディア露出を増やす | ③共起戦略 |
| コンテンツ作るがLLM引用されない | 結論→根拠→具体例の構造に書き直す | ②抽出されやすい構造 |
| AI生成記事で量産したい | やめる。一次情報・独自見解を人手で追加 | ②③E-E-A-T低下リスク |
| 業界の権威性が欲しい | 専門家インタビュー・独自データ調査を公開 | ③一次情報の保有 |
| 効果測定したい | 主要LLMでの定期クエリチェックを月次運用 | ①④監視ループ |
| Wikipediaに載せたい | 中立的・出典付きで第三者経由で立てる | ①③学習データ侵入 |
