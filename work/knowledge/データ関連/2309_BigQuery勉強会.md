# BigQuery勉強会 — 広告運用における活用と予測LTV配信の全体像

## 出典
- ファイル: BigQuery勉強会.docx
- 種別: 社内勉強会資料
- 作成時期: 2023年9月（yymm = 2309）

## 用途（どんな時に活用できるか）
- GA4データをBigQueryに連携してCRM分析を行い、広告施策に示唆を還元したいとき（例: 「優良顧客が初回来訪した流入経路」を特定して媒体配分を見直す）
- クライアントが「pLTV配信」「価値ベース入札」を検討している際、データ基盤・予測モデル・媒体連携の論点を整理したいとき
- データ基盤（GA4 / BigQuery / Looker / DATAGEAR等）の構成を提案する場面で、各レイヤーの役割と費用構造を説明する必要があるとき
- 自社/クライアントの「サイト内行動 × 受注顧客データ」を突合した独自マスタを作り、機械学習で目的変数（購買・LTV）を予測したいとき
- 予測モデル導入PJTで、モデル評価指標（ROC / AUC）や特徴量寄与度の見方をディレクターとして押さえておきたいとき

## 概要
BigQuery（以下BQ）は、Googleが提供するクラウド型のデータウェアハウス。表形式の大量データを安価かつ高速に保持・分析でき、GA4・Google広告・Lookerなど他Googleプロダクトとの連携が容易である点が広告領域での最大のメリットになる。

広告の文脈では、BQは大きく2つの役割で使われる。1つ目は「優れた分析ツール / CDP的な役割」としての使い方で、GA4の生データやCRMデータをBQに集約し、CRM分析の結果を媒体運用に還元する。2つ目は「予測モデル基盤」としての使い方で、BigQuery ML（BQML）を用いてLTV・購買確率などの予測モデルを構築し、その予測値を媒体に返すことで価値ベース入札（pLTV配信など）を実現する。

特にpLTV配信では、GA4のクリックIDに紐づく行動データと、顧客IDや受注IDに紐づく顧客データをBQ上で突合してマスタ化し、そこからモデルを構築 → クリックIDごとの予測LTVを日次で媒体に返す、という流れが基本形となる。BQはこの「突合・モデル構築・予測値出力」のハブとして機能する。

料金は完全な従量課金で、「ストレージ料金（データを置く対価）」と「クエリ料金（演算する対価）」の2軸で発生する。設計時はクエリ料金の抑制（パーティション・スキャン量）を意識する必要がある。

## 本文構造

### 1. pLTV配信の決め手
pLTV（予測LTV）配信を導入する際、どの構成で行くかの判断軸として以下が挙げられる。

- 変数になるデータ変更の幅（= PDCAの回しやすさ）
- 開発 / ランニングコスト（保守費用、ツール利用料）
- 開発負荷

> ツール選定や内製/外注の判断時に、単に「予測精度が高いか」だけでなく、「変更しやすいか」「コストが見合うか」「自社で運用しきれるか」を並べて比較する観点。

### 2. 予測モデルのイメージ
予測モデルとは、それぞれの特徴（説明変数）が「出世する／しない」（目的変数）にどれくらい影響を与えているのかを分析し、その関係を確率の数式（モデル）として表現したもの。機械学習でやっているのは、この「確率の数式を作ること」に他ならない。

- 目的変数: 予測したい結果（例: 購買する/しない、LTV金額）
- 説明変数: 結果に影響しうる特徴（例: 流入チャネル、来訪タイミング）

### 3. DATAGEAR説明変数（具体例）
DATAGEAR等で予測モデルに投入される説明変数の例。

- 流入チャネル
- 来訪タイミング
- セッション後の行動（滞在時間、ページビュー、スクロール等）
- デバイス
- など

### 4. pLTV配信までの流れ
1. GA4上でのクリックIDに紐づくデータと、顧客IDや受注IDに紐づく顧客データをBigQuery上で突合する  
   → BigQuery上に「サイト内行動データ × 顧客情報」が一覧化されたマスタが形成されるイメージ
2. そのマスタをもとに予測モデルを構築する
3. クリックIDごとに予測LTV値を媒体に（日次で）返すことで、媒体側の最適化に活用する

> BQは「データ統合のハブ」「モデル構築の場」「媒体への予測値受け渡しの起点」を一手に担う構成になる。

### 5. BigQueryの特長3つ
1. **表形式のデータを大量に保持・分析できる**（Excelの上位互換のような存在）
2. **従量課金制であり、類似サービスに比べて安価**。課金対象は2種類。
   - **ストレージ料金**: データを保持すること（= 場所のリソースをGoogleから借りること）への課金
   - **クエリ料金**: クエリを実行すること（= 演算のリソースをGoogleから借りること）への課金
3. **Google製品との連携がしやすい**  
   BQ内のデータをLookerで可視化したり、GAで収集したデータをBQに吐き出して分析したり、といったツール連携が容易。

### 6. 広告におけるBigQueryの活用（2パターン）
1. **BigQueryでCRM分析をし、得た示唆を広告に活かす**  
   BQを「優れた分析ツール / CDPのような役割」で使う。例: 優良顧客のセグメント特性を分析して、媒体側のターゲティング・クリエイティブ設計に反映する。
2. **BigQueryで予測モデルを作成し、広告を最適化する**  
   BQML等で予測モデルを構築し、その予測値を媒体に返して入札最適化に活用する（pLTV配信が代表例）。

### 7. BigQuery上での予測モデルの作り方（一般的な手順）
BQML（BigQuery ML）を用いる場合の標準的な手順。

1. **データを用意する**
2. **予測モデルを作る** （`CREATE MODEL ...`）
3. **予測モデルを評価する①: モデルの精度を知る** （`ML.EVALUATE ...`）
4. **予測モデルを評価する②: 特徴の貢献度を見る** （`ML.WEIGHTS ...`）
5. **予測モデルを使って予測する** （`ML.PREDICT ...`）

> ②〜④を行き来してブラッシュアップし、最終的に活用する。一発で完成形を作るのではなく、評価→説明変数の見直し→再学習のループを回すのが前提。

**SQL構文イメージ（BQML標準形）:**

```sql
-- 2. モデルを作る（例: ロジスティック回帰で購買有無を予測）
CREATE OR REPLACE MODEL `project.dataset.purchase_model`
OPTIONS(
  model_type = 'LOGISTIC_REG',
  input_label_cols = ['is_purchase']
) AS
SELECT
  is_purchase,
  channel,
  visit_hour,
  session_duration,
  page_views,
  device_category
FROM
  `project.dataset.training_data`;

-- 3. モデルの精度を見る（ROC / AUC など）
SELECT *
FROM ML.EVALUATE(MODEL `project.dataset.purchase_model`);

-- 4. 各説明変数の貢献度（重み）を見る
SELECT *
FROM ML.WEIGHTS(MODEL `project.dataset.purchase_model`);

-- 5. 新しいデータに対して予測する
SELECT *
FROM ML.PREDICT(
  MODEL `project.dataset.purchase_model`,
  (SELECT * FROM `project.dataset.scoring_data`)
);
```

**モデルタイプの選び方:**
- 「購買する／しない」など分類する場合は **ロジスティック回帰**（`LOGISTIC_REG`）。
- それ以外（連続値の予測など）はBQMLが提供する他モデル（線形回帰、ブースティング系など）から選択。

- BQML概要（Google公式）: https://cloud.google.com/bigquery/docs/bqml-introduction?hl=ja

### 8. モデル評価指標の押さえどころ（③の評価フェーズ）
評価タイミングでは **`roc_auc_score`** で評価するのが基本。

- **ROC曲線**: Y軸 = 真陽性率（予測が当たっている割合）、X軸 = 偽陽性率（予測が間違っている割合）で描く曲線。
- **AUC（Area Under the Curve）**: ROC曲線の下の領域の面積。**AUCが大きいほど成果がいい（=判別精度が高い）** と判断できる。

> ディレクターとしては「AUCを見れば、このモデルがどのくらい賢いか分かる」と覚えておけばOK。0.5に近いとランダムと同じ、1.0に近いほど優秀。

参考リンク:
- ROC / AUCの直感的説明: https://qiita.com/TsutomuNakamura/items/a1a6a02cb9bb0dcbb37f
- ROC曲線とAUCの読み方: https://atmarkit.itmedia.co.jp/ait/articles/2208/08/news034.html

## 太一視点の示唆 / 次のアクション

**ディレクターとして押さえるべき「BQ活用の最小セット」:**

1. **BQの位置付けを一言で言えるようにする**  
   「大量データを安く保持・演算できる、Googleエコシステムの中心になるDWH」。クライアントへの説明はここから入る。

2. **料金構造を「ストレージ ÷ クエリ」で分けて理解する**  
   見積もり/コスト懸念の質問が来たとき、「保持するデータ量」と「クエリのスキャン量」の2軸で答えられるようにする。クエリ料金の抑制（パーティション・必要カラムのみSELECT）は提案時の差別化ポイント。

3. **広告でのBQ活用は「CRM分析 → 示唆還元」と「予測モデル → 入札最適化」の2系統と覚える**  
   提案時はどちらの系統の話をしているのか明確に切り分ける。混ぜると要件が曖昧になる。

4. **pLTV配信の3ステップ（突合 → モデル構築 → 媒体返し）をクライアント説明用にテンプレ化する**  
   特に「クリックIDと顧客IDをBQ上で突合する」というキー概念は、データ要件定義の出発点になる。

5. **BQMLの5ステップ（用意 → CREATE MODEL → EVALUATE → WEIGHTS → PREDICT）を頭に入れる**  
   実装はエンジニア / アナリストが担うが、ディレクターが流れを知っているとPJT管理の解像度が一段上がる。特に「EVALUATEとWEIGHTSを行き来してブラッシュアップする」工程の存在を理解しておく。

6. **モデル精度の話が出たら "AUC" で会話できるようにする**  
   「AUCいくつ出てます？」と聞けるだけで、データチームとの対話の質が上がる。0.7台 = 実用ライン、0.8以上 = かなり良いの肌感を持つ。

7. **次の実務アクション候補**
   - 担当クライアントのうちGA4 → BQエクスポートを設定している案件をリストアップし、「BQで何を分析すれば運用に効く示唆が出るか」を1案件1テーマで仮説出しする
   - pLTV配信 / 価値ベース入札の可能性がある案件（受注金額にばらつきが大きい / リピート構造がある）を3社ピックアップし、データ突合の要件（クリックID・顧客ID・受注テーブル）が揃うか棚卸しする
   - 自分用にBQML公式ハンズオン（cloudskillsboost）を1本走り切り、`CREATE MODEL` → `ML.EVALUATE` → `ML.PREDICT` の流れを手を動かして体験しておく
