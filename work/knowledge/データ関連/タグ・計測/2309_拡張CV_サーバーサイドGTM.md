# 拡張コンバージョン / サーバーサイドGTM の活用 — Cookie規制時代の計測精度と1st Partyデータ戦略

## 出典
- ファイル: 拡張CV・サーバーサイドGTM.docx
- 種別: 社内資料（Google主催の勉強会内容を整理したもの）
- 作成時期: 2023年9月（yymm = 2309）

## 用途（どんな時に活用できるか）
戦略家視点で「この資料を引っ張り出すべき具体的シーン」を以下に整理する。

1. **Cookie規制（ITP・3rd Party Cookie廃止）の影響で計測精度が落ち、CV数が実態と乖離していると感じたとき**
   - 「最近CV計測が減っている気がする」「機械学習の最適化が効きづらい」というクライアントの相談を受けたタイミングで、拡張CV / SS-GTMという選択肢を提示する根拠資料として活用。

2. **P-MAX / 検索広告 / YouTube for Action の機械学習の精度を底上げしたいとき**
   - 入札最適化の燃料となるCVデータの質と量を改善する打ち手として、最初にあてる施策候補となる。

3. **EC・予約・会員登録など「PIIを伴うCVが取れるクライアント」の高度化提案をするとき**
   - メアド・電話番号・住所がCV時に取得できるビジネス（EC、人材、不動産、教育、金融など）では、拡張CVは導入の障壁が低く、リフトも大きいので最有力提案カードとなる。

4. **GMP / sGTM導入のような中長期の1st Partyデータ基盤構築を提案するとき**
   - 単発のCPA改善ではなく「データ基盤を持つことが競争優位になる」という大きなストーリーで提案する際の論拠。カスタマーマッチや新GA4アトリビューションなどの隣接施策とセットで提示する。

5. **広告効果が同業他社と比べて伸び悩んでいるクライアントの差別化施策を考えるとき**
   - 「他社がまだ手をつけていない計測強化」を切り口に、運用面ではなく計測面の改善で打開する提案ができる。

## 概要
本資料は、Cookie規制（ITP、3rd Party Cookie廃止）が進む中で、**広告計測精度を維持・向上させるためのGoogleのソリューション2種**を整理したものである。

ひとつは **拡張コンバージョン（Enhanced Conversions）**。サイト上でCVが発生した際に、ユーザーが入力したメールアドレス・電話番号・氏名/住所などの1st Party データをハッシュ化してGoogleに送信し、Googleが保有するログインユーザー情報と突合することでCV計測の取りこぼしを補完する仕組み。Search で +3.5〜5%、YouTube for Action で +12% のCVR改善（中央値）が見込める、ROI観点でコストパフォーマンスの高い施策である。

もうひとつは **サーバーサイドGTM（sGTM）**。従来クライアント側のJavaScriptで発行していたCookieを、自社ドメイン配下のサーバー（GCP上のコンテナ）から発行することで、ITPの24時間制限を回避し、計測の取りこぼしを抑える。同時にデータをサーバー側で一元処理することでページ表示速度の改善とセキュリティ強化も実現する。GCP契約と技術リソースが必要なため、拡張CVより導入ハードルは高い。

両者はいずれも単独の計測改善ツールではなく、**「1st Party データを活用したマーケティング基盤」を構築するための入口**として位置づけられている。導入の推奨順は ①拡張CV → ②サーバーサイドGTM。さらにその先には、カスタマーマッチ（ターゲティング強化）、GA4アトリビューション（メディア横断評価）など、1st Partyデータを活用した一連の施策群が広がっている。

## 本文構造

### 1. なぜ今、拡張CV・サーバーサイドGTMなのか

#### 背景
- ITP / 3rd Party Cookie廃止の影響で、従来のCookieベース計測ではクリックから24時間以上経過したCVが直接計測できなくなりつつある。
- 結果として、機械学習の入札最適化に渡せるCVシグナルが減少し、広告パフォーマンスそのものが劣化していくリスクがある。

#### Googleの位置づけ
- 単なる「計測精度の向上」ではなく、**1st Party データの活用によるビジネス全体の推進**を目標としているとGoogleは強調。
- そのための代表的ソリューションが「拡張CV」と「サーバーサイドタグ」の2つ。

> CV計測精度の向上のためだけではなく、1st Party データの活用によるビジネス全体の推進を目標としている

---

### 2. 拡張コンバージョン（Enhanced Conversions）

#### 仕組み
1. ユーザーがGoogleアカウントにログインした状態で広告に接触。
2. サイト上でCV（購入・登録など）が発生。
3. CVタグ発火時、入力されたメアド/電話/住所等の1st Party データを **ブラウザ側でハッシュ化** してGoogleに送信。
4. Google側が保有するハッシュ化済みログイン情報と突合し、推定CVと合算してGoogle Adsのレポートに反映。

#### マッチングKey
- 利用可能データ: **メールアドレス、電話番号、居住地/氏名**
- データ点数が多いほどマッチング率は上がる。
- **電話番号単体送信は不可。メアド or 住所のいずれかが必須セット**。

#### インパクト（中央値）
| プロダクト | CVR改善幅 |
| --- | --- |
| Search | +3.5〜5% |
| YouTube for Action | +12% |

- これは「Googleがすでに推定CVを持った状態」での追加リフト。
- 「Facebookの方がCAPIで改善幅大きい」と言われる場合があるが、それはFacebook側が推定CVゼロからのスタートだったため。前提条件の違いに注意（Google談）。

#### パフォーマンス改善のメカニズム
> CV増加 → モデリングとトータルCVの精度向上 → 入札 & アトリビューションの改善 → パフォーマンスの改善

つまり、計測のリフトはそのまま機械学習・入札最適化の燃料になり、CVRだけでなくCPAやROAS全体に波及する。

#### レポート反映タイミング
- Search: 60日以内
- YouTube: 30日以内
- 反映後はリアルタイム更新。
- 推定CVと合算表示される。

#### 対応プロダクト
- 対応: **Search / YouTube for Action**（Googleオウンドメディアのみ）
- 非対応: GDN、YouTube for Action以外のYouTube、Local、App、Find（FINDS）
- SA360 / GA4 連携: 開発中（資料時点）
- App上でのCVは未対応（接触媒体に関わらず）。
- iOS14.5 / YouTube App内広告接触は未対応だが今後対応予定。

#### 設定の前提（適用要件）
1. **サイトワイドタグの設定**: gtag.js または GTM。
2. **Google Ads の CVタグを使用していること**: GAやオフラインCVは現時点でサポート外。
3. **顧客データを適切に送信できること**: 登録・購入など「PIIを伴う深いCV」に向く。
4. **業種制限**: アルコール、政治、宗教、健康などセンシティブカテゴリは対応不可。

#### 実装の3パターン
| 方式 | 内容 | 適するケース |
| --- | --- | --- |
| **タグ利用（自動設定）** | Google Ads管理画面のチェックボックスで有効化 / GTM UIから設定 | CV完了ページに1st Partyデータが存在し、自動取得が成立する環境 |
| **タグ利用（手動）** | JavaScript / CSS で取得位置を明示指定 | CV完了ページのソースに1st Partyデータが無く、自動取得できない環境 |
| **API連携** | 広告主データベースから直接GoogleにPIIを送信 | すでにFacebook CAPI導入済など、データ連携基盤がある広告主 |

> 最終的なCVページで1st Party Dataが存在するかどうかで、データの取得有無が変わる。ソースに1st Party Dataがない場合は手動設定

#### 1st Party データを起点にした派生活用
- **広告効果測定**: 拡張コンバージョン
- **ターゲティング**: カスタマーマッチ

→ 同じ1st Partyデータが、計測とターゲティングの両方の燃料になる。導入を「単発のCV補完」と捉えず、データ資産化の文脈で提案するのが筋。

### 3. サーバーサイドタグ（sGTM）

#### 何が嬉しいのか
- **計測精度の向上**: ITPの24時間Cookie制限を回避できる。
- **サイトパフォーマンス改善**: ブラウザ側で動くタグ数を減らせる。
- **セキュリティ強化**: ユーザーブラウザ → GAサーバーの直接送信を、自社サーバーを経由する形に変換できる。

#### Cookieの扱いと従来計測との違い
- **従来計測（クライアントサイドGTM）**:
  - JavaScriptで発行された1st Party CookieはITP対象 → 24時間で消える → CTから24時間以上経過したCVは取れない。
- **サーバーサイドGTM**:
  - 自社ドメイン配下のサーバーからCookieが発行される → Googleドメインからではなく自社ドメインから出る純粋な1st Party扱い → ITPの24時間制限を受けない。

#### アーキテクチャ
- Web用コンテナ（従来のGTM）に加えて、**サーバー用コンテナ**が必要。
- サーバー用コンテナのホスト先として **GCP（Google Cloud Platform）** を利用する。

#### 対応プロダクト（GTM上でコンテナテンプレートあり）
- **対応済み**: Universal Analytics / GA4 / Measurement Protocol / Google Ads
- **対応中**: SA360 / DV360 / CM360
- **Facebook CAPI**: GTMテンプレが存在
  - 参考: [Facebook CAPI Help Center](https://www.facebook.com/business/help/2041148702652965?id=818859032317965)

#### 実装要件
1. **体制**: GCP/GTMを技術的に理解した実装パートナーの協力が必須。
2. **契約**: GCPの契約 + GCP有償サポート契約。
3. **技術前提**: GTMでGA4をすでに実装済 / サイトワイドタグの設定が完了していること。

#### 費用
- GTMサーバー用コンテナ自体は無料。
- ただし **GCP利用料（インフラ費用）** が発生（ランニング）。
- GCP有償サポートの契約料も発生。
- 参考: [Google Cloud カスタマーケア](https://cloud.google.com/support?hl=ja)

#### 検証 / 留意事項
- テストプロパティでの検証を推奨。GA4は無償なので検証コストは抑えられる。
- **サーバー用コンテナはベータ版扱い**、GTMのSLAは対象外。
- クロスドメイントラッキングはホワイトリスト登録不要。
- Optimize(360) は未対応。
- **拡張CVとサイトワイドタグの同時検証は非推奨**（干渉リスク）。

### 4. 拡張CV と サーバーサイドGTM の比較

| 観点 | 拡張CV | サーバーサイドGTM |
| --- | --- | --- |
| 業界要件 | あり（アルコール / ヘルスケア / 政治 / 宗教はNG） | なし |
| 技術要件 | サイトワイドタグ（GTM or gtag.js） + PII を伴うCV | サイトワイドタグ + GTM + GA4 + GCP（初期/ランニングコスト有） |
| Google広告対応フォーマット | Search / YouTube (for Action) | Search / Display / YouTube |
| 対応するCV / 指標 | PII入力を伴うもの（オンラインでの購入・予約等） | 購入・予約 + 各種マイクロCVにも対応 |

#### 導入順の推奨
- まずは拡張CVから着手 → 必要に応じてサーバーサイドGTMへ拡張、というのがGoogle推奨パス。
- 拡張CVは導入工数が小さく、効果が早く出るため「やらない理由がない」レベル。sGTMはGCP契約や開発リソースが必要なため、計測の重要度・規模が大きい広告主向け。

#### その先のアプローチ例
- **ターゲティング強化**: ポリシー確認 → カスタマーマッチでエンゲージメント強化
- **メディア横断評価**: 新GA4アトリビューション → ジャーニー可視化と成果評価
- **離脱予兆ユーザー対策**: 新GA4アトリビューション → 購入/離脱の可能性が高いユーザーへのアプローチ

→ 拡張CV / sGTM はあくまで「1st Party データ活用基盤の入口」。後続のターゲティング・分析施策が本丸。

### 6. Q&A ピックアップ

- **Q. CVページにユーザーデータがない場合、拡張CVは取れないか？**
  - A. API経由で送付すれば対応可能。
- **Q. VAC（Video Action Campaign）は対応しているか？**
  - A. 対応している。
- **Q. SSC（Smart Shopping Campaign）は対応しているか？**
  - A. 要確認（資料時点では未確定）。
- **Q. カスタマーマッチのハッシュ化はセキュリティ上問題ないか？**
  - A. 一方向ハッシュ（復号不可）。心配であればGoogleに個別相談。
- **Q. カスタマーマッチのマッチ率はどのくらいか？**
  - A. クライアントのビジネスによる。Gmailアカウントに紐づくアドレス比率が高いほどマッチ率は高い。docomoなど他キャリアドメインが多いと低くなる傾向。

## 太一視点の示唆 / 次のアクション

### 導入判断のチェックリスト（CSとして提案前にチェックすべき項目）

#### 拡張CV を提案するかの判断軸
1. **CV時にPII（メアド・電話・住所）が取得できているか？** → Yes なら導入余地大。
2. **業種制限に該当しないか？** → アルコール / ヘルスケア / 政治 / 宗教でないかを最初に確認。
3. **Google Ads CVタグを使っているか？（GA経由ではないか？）** → 使っていれば即対応可。GA経由なら設定変更が必要。
4. **CV完了ページにPIIが残っているか？** → 残っていれば自動設定、残っていなければ手動 or API。
5. **規模感的にやる意味があるか？** → CVR +3.5〜12%のリフトなので、月CV数が3桁以上ある案件は確実にペイする。CV数が極端に少ない案件は優先度を落としてよい。

#### sGTM を提案するかの判断軸
1. **GA4実装済 / サイトワイドタグ完了済か？** → 前提条件を満たしていないと門前払い。
2. **広告主側にエンジニアリングリソースがあるか？** → GCP契約 / 実装 / 保守の体制が必要。
3. **GCP費用（月数万〜数十万のオーダー）を見込めるクライアントか？** → 中堅以上の広告主向け。
4. **マイクロCVも含めて高精度に計測したい強い動機があるか？** → 単純なCV補完だけなら拡張CVで十分。sGTMは「データ基盤を持ちたい」明確な意図が必要。

### 提案ストーリー
- 「ITP / Cookie規制下でCV計測の取りこぼしが起きている」という背景説明 → 「拡張CVで Search +3.5〜5%, YouTube +12% のリフトが見込める」という具体数値 → 「実装はCVタグのチェックボックスのみで完結する案件もある」という工数感を提示するのが王道。
- sGTMは「短期施策」ではなく「中期のデータ基盤投資」として、年間予算検討のタイミングで切り出すのが筋。

### 工数感
- **拡張CV（自動設定）**: 1〜数時間。CVタグの設定変更のみ。
- **拡張CV（手動設定）**: 開発工数発生（CSS/JS指定、数日〜1週間）。
- **拡張CV（API連携）**: 広告主側のデータベース連携要件次第。1ヶ月〜。
- **sGTM**: 初期構築だけで1〜3ヶ月、GCPランニング月数万円〜。

### 自分が次に取るべきアクション
1. 担当案件のうち、**PIIを伴うCVを持っているクライアント** をリストアップし、拡張CV未導入のものを洗い出す。
2. 業種制限に該当しない案件について、自動設定で導入可能かをCV完了ページのソースで確認する。
3. 月CV数が多い順に提案優先度を付け、1社目から導入トライ。
4. sGTMは「年次予算 / 中期計画」の議論タイミングで、GA4移行とセットで提案する形に整える。
5. 隣接ナレッジ（同フォルダ内の `ITPが計測ツールに与える影響とGoogleの機能.docx` / `ITP対策に活用できるGoogleのソリューション.docx` / `【RH】Cookie-ITP勉強会.pptx`）と組み合わせて、Cookie規制対応の体系的提案資料に発展させる。
