# アイレップ標準パラメータ命名規則 — U2構造×ValueTrackによるパラメータ管理規約

## 出典
- ファイル: アイレップ標準パラメータ.docx
- 種別: 広告代理店（アイレップ）標準パラメータ規約
- 作成時期: 2023年9月（yymm = 2309）

## 用途（どんな時に活用できるか）
- 新規クライアントのUTMパラメータ設計をゼロから行う際、業界標準としての命名規則を参照したいとき。
- 広告計測ルール（リスティング／ディスプレイ／Facebook／YDA）を社内・案件横断で統一する必要が出たとき。
- KW追加や入稿のたびに手動でパラメータを発行している運用を、`{ValueTrack}` 自動置換ベースに刷新したいとき。
- LP／TDトライアル（ABテスト）を実施したいが、従来のKW単位パラメータ運用では実施できず行き詰まっているとき。
- GA・Adobe Analytics・Tableau に外部CVを紐づける際、媒体側からどの粒度（KW／広告／キャンペーン／サイトリンク）まで取得できるかを設計したいとき。
- 既存の最終リンク先URLに直接パラメータが書かれている案件を、トラッキングテンプレートに切り出すリファクタを行うとき。

## 概要
本資料は、アイレップ社が定義する「広告媒体側で計測パラメータを最も効率的・安全に取得するための標準命名規約」をまとめたもの。中核は **U2構造（Upgraded URL構造）** と **ValueTrack** の組み合わせで、KW・広告ごとにユニークなパラメータを発行しつつ、入稿時の人的工数をほぼゼロにすることを目的としている。

そもそもパラメータとは「どこから来たか」という情報を解析ツールに渡すための目印であり、設定の基本原則として **下層の粒度の設定が優先される**（KWに設定があればKWが、広告グループに設定があればグループが優先）。この性質によって、従来は「KW単位でパラメータを付けないと粒度が取れない」という制約があり、KW追加のたびにURLを発行する／LPトライアルができない／PC/SP出し分け時に `{ifmobile:}{ifnotmobile:}` の確認が大変、といった弊害が発生していた。

U2構造は、最終リンク先URL／トラッキングテンプレート／カスタムパラメータの3層を使い分け、**アカウントやキャンペーン単位でパラメータをまとめて管理できる**ようにした構造である。ValueTrack（`{keyword}` `{creative}` 等の命令文）と組み合わせると、媒体が自動でKWID・広告IDなどを動的に挿入してくれるため、自分でカスタムパラメータをマスタ管理する必要がなくなり、入稿事故が起こらなくなる。

実践メリットは大きく5つ：(1) パラメータ設定不備（補填・事故）の削減、(2) より細かい粒度での指標モニタリング、(3) オペレーション工数の大幅削減、(4) 外部CV紐づけ依頼の納期短縮、(5) 高速なPDCAサイクル実現。

## 本文構造

### 1. U2構造（Upgraded URL構造）とは

| 項目 | 従来構造 | U2構造 |
|---|---|---|
| パラメータ付与単位 | KWや広告ごとに個別に1つずつ付与 | アカウント・CP・広告グループ単位でも管理可能 |
| LP/TDトライアル | 不可（KW単位で固定されるため） | 可能（広告単位でLPパラメータを差し替えられる） |
| 管理対象 | 最終リンク先URLにすべて記述 | 最終リンク先URL／トラッキングテンプレート／カスタムパラメータの3層に分離 |
| 出し分け | URL本体に書き込み | カスタムパラメータでCP・広告グループごとに出し分け |

**ポイント**：上位コンポーネント（アカウント／キャンペーン）でもトラッキングテンプレートとカスタムパラメータを利用してパラメータを管理できるようになったため、KW単位でなくてもLPのパラメータを返せる。これにより「KWのパラメータをきちんと返しながら、LPのパラメータもきちんと返せる」状態が実現する。

### 2. ValueTrack — 動的置換命令文

ValueTrackは「この場所にこのデータを持って来い」という命令文。所定の位置に書き込むと、媒体側が所定のデータを動的に格納してくれる。これによりカスタムパラメータの静的発番（人間によるマスタ管理）が不要になり、事故が起こらない。

主要なValueTrack：

| ValueTrack | 取得できるデータ | 返り値の例・注意点 |
|---|---|---|
| `{keyword}` | キーワード | — |
| `{matchtype}` | マッチタイプ | `e:exact` / `p:phrase` / `b:broad` |
| `{targetid}` | ターゲットID（KW・自動ターゲット・リタゲリストの条件ID） | ユーザーリスト計測にも利用 |
| `{device}` | デバイス | `c:computer` / `t:tablet` / `m:mobile` |
| `{creative}` | クリエイティブID（広告ID） | D&E（Dynamic Search Ads等）利用時は重複に注意 |
| `{campaignid}` | キャンペーンID | — |
| `{adgroupid}` | 広告グループID | — |
| `{feeditemid}` | サイトリンクID | サイトリンク粒度の計測に使用 |
| `{lpurl}` | 最終リンク先URL | トラッキングテンプレート先頭で必須 |

**集計の制約**：従来のURL構造では集計がKWのパラメータに依存していたため、「広告とKWの両方」「KWとサイトリンクの両方」という同時粒度集計は不可能だった（どちらか一方なら可）。広告グループ集計は、KWの成果合算で行えるためグループあたりの広告本数・KW数によらず可能。なお **検索クエリを取得するValueTrackは現状（2309時点）存在しない**。

### 3. アイレップ標準パラメータの全体構造（基本形）

アカウント単位のトラッキングテンプレートに記述する標準形：

```
{lpurl}?utm_source=yahoo&utm_medium=cpc&utm_term={matchtype}_{keyword}&utm_campaign={_campaign}_{campaignid}_{adgroupid}_{creative}_{targetid}&utm_id=yss_{creative}
```

（YahooSSの例。`[アカウントID]` 相当の値は手動で挿入する必要がある）

### 4. utm_パラメータ別 取得内容（標準項目）

| 設置場所（utm_キー） | 設置内容 | ValueTrackで取得するデータ |
|---|---|---|
| `utm_source` | yahoo / google / facebook 等の媒体名（静的） | — |
| `utm_medium` | チャネル（cpc / social 等、静的） | — |
| `utm_campaign` | キャンペーン名（クライアント指定）＋ID系の連結 | `{_campaign}_{campaignid}_{adgroupid}_{creative}_{targetid}` |
| `utm_term` | キーワード | `{matchtype}_{keyword}` |
| `utm_content` | 広告ID／広告グループID／ターゲットID等 | `{creative}` / `{adgroupid}` / `{targetid}`（キーワードID・動的検索広告のターゲットID・リマーケティングリストID・商品分類ID も含む） |
| `utm_id` | 広告ID（媒体プレフィックス付き） | `yss_{creative}` 等 |

### 6. GA／Adobe Analyticsでの活用

- **GA**：アカウント単位でアイレップ標準パラメータを設定し、キャンペーンのカスタムパラメータに「キャンペーン名をエンコードしたもの」を `{_campaign}` に流し込むことで、GA上でキャンペーン名を **日本語のまま表示** できる。
  - 設定形：キャンペーンのカスタムパラメータで `{_campaign}=（キャンペーン名をエンコードした文字列）` を設定。
  - エンコードはExcelの `ENCODEURL` 関数で簡単に作成可能。
  - `[アカウントID]` は手動で挿入する必要がある。
- **Adobe Analytics**：標準パラメータ構造を流用可能。
- **Tableau**：外部CV紐づけを行えば、自動で外部CVの紐づけが可能。

### 7. 入稿内容の変更プロセス（既存案件の移行手順）

標準パラメータ実装のために行うこと：
1. 設定変更前後のトラッキングテンプレートを、周囲の担当者がWチェックできる形でFMT（フォーマット）に記入する（資料詳細参照）。
2. 管理画面上でトラッキングテンプレートにアイレップ標準パラメータを記入して保存する（MGRや案件の品質管理担当と一緒に確認）。
3. 既存変更の場合は外部CV紐づけ先が変わるため **外部CVチームに問い合わせ**。新規案件の場合も外部CVチームに問い合わせ。

**注意点**：審査が入るためラグがある（審査完了までは従来設定が引き継がれる）。

**広告の最終リンク先URLに既存のパラメータが設定されている場合のプロセス**：

| ステップ | 内容 | 例 |
|---|---|---|
| i | 既存の最終リンク先URLのパラメータ部分を除いた最終ページURLを設定した広告を **新規入稿** | before: `https://www.irep.co.jp?utm_source=google`<br>after: `https://www.irep.co.jp` |
| ii | 審査が通り次第、既存広告を停止 | — |
| iii | アカウントトラッキングテンプレートにパラメータ項目を切り出して設定 | — |
| iv | 次回以降の広告は **トラッキングテンプレートなし** で入稿 | — |

### 8. ValueTrackで計測できる集計単位（まとめ）

| 集計したい単位 | 使用するValueTrack |
|---|---|
| ユーザーリスト | `{targetid}` |
| 広告グループ | `{adgroupid}` |
| 広告 | `{creative}` |
| サイトリンク | `{feeditemid}` |
| 検索クエリ | **対応するValueTrackは現状存在しない** |

`finalURL` と `Tracking template` を分けて管理できるようになったため、広告ごとに異なるLPを設定し、各集計単位で成果を計測することも可能。

## 太一視点の示唆 / 次のアクション

- **「KW単位パラメータ運用」が残っている案件は移行コストを払う価値が高い**。U2構造×ValueTrackの真価は、入稿事故ゼロ＋LPトライアル可能化＋外部CV連携の高速化という複合効果。単発の工数削減ではなく、PDCAサイクルの回転数自体が上がる施策として位置付けるべき。新規クライアント受任時は最初からこの構造で入稿する前提を置く。
- **CV紐づけ先が変わる移行は外部CVチームへの早期相談がボトルネック**。審査ラグも含めると着手から計測安定まで数日〜1週間規模。クライアント向けには「移行週は数値断絶があり得る」と事前合意しておく運用が必要。
- **`{_campaign}` をクライアント指定キャンペーン名で日本語表示する設計**は、GAレポートをそのままクライアント共有する案件で大きな差別化になる。ENCODEURL関数によるエンコード一覧をテンプレ化し、入稿時に貼り付けるだけにしておくと品質安定。
- **YDAだけはトラッキングテンプレートが存在しない**ため例外運用になる点に注意。広告URL本体に直書きするので、コピペミスがリスク。媒体別チェックリストでYDAだけ別欄を設けるのが安全。
- **Facebookは `{{...}}` 構文＋`?` 不要**という独自仕様。YSS/GoogleAds用のテンプレを流用しがちなので、媒体ごとにテンプレを分離して `utm_source` 値とともに固定化しておく。
- **検索クエリのValueTrackが存在しない**問題は、検索クエリレポートをCV結果と突き合わせる場合は媒体管理画面側のレポート機能に依存することを意味する。Tableau連携で補えるかどうかを案件ごとに判断する。
- **D&E（Dynamic Search Ads等）利用時の `{creative}` 重複**は計測精度を毀損するため、動的検索広告を多用するEC・大型サイト案件では別途設計が必要。`{_campaign}` 側でカスタム識別子を補う等のローカルルール検討余地あり。
- **他規約との差異の見立て**：本規約は「アカウント単位トラッキングテンプレ＋カスタムパラメータ＋ValueTrack」という3層構造を前提とする運用フレームで、UTMキー（source/medium/campaign/term/content/id）の標準名はGA推奨に揃いつつ、`utm_content` に複数IDを「`_`」で連結する独自仕様が特徴。社内独自規約を作る場合も、この連結仕様の互換性（既存BIツールがパースできるか）は必ず先に検証する。
