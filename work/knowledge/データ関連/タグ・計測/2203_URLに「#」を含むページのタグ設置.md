## 用途（どんな時に活用できるか）
クライアント案件でGTM/GA計測を組む際、以下のような「URL末尾に `#` が出てくる」サイトに当たったときの設計図として使う。

- **SPA（Single Page Application）/ Vue・Reactのハッシュルーティング** で `https://example.com/#/about` のようにページ遷移時に `#` 以降だけが変わる構成。通常の「ページビュー」トリガーだと初回しか発火せず、遷移後のページが計測できない。
- **電子書籍・PDFビューワー・カタログサイト** で `?id=xxx#/page=6` のようにページ番号が `#` 以降で表現される構成。「最後のページに到達した」をCV計測したいとき。
- **長尺LP内のアンカージャンプ** （`#feature01`、`#cv`等）でセクション到達を計測したいとき。
- **CV直前のフォーム遷移／サンクスページ** が `#thanks`のようにハッシュで切り替わる仕様で、本来CVが計上されない／全PVで誤発火している状態を是正したいとき。
- **GA4/UA移行・GTM新規導入の初期診断時** に「Page URLにハッシュが入っているのにGAに送られていない」というズレを発見したとき。

## 概要
URLの `#`（ハッシュ／フラグメント識別子／アンカーリンク）以降の文字列は、ブラウザ内部だけで処理される領域であり、サーバーへは送信されない。結果として **GoogleアナリティクスにはURLの `#` 以降が届かず、Page URL/Page Path系の計測値はすべて `#` 直前で切れた状態になる**。

さらに、ハッシュ部分のみが変化するページ遷移（pushState/hashchange）は **ブラウザの通常の「ページビュー」イベントを発生させない** ため、GTMのデフォルトの「ページビュー」トリガーでは検知できない。これにより、「アンカー先のセクションでCVタグを発火させたい」「ハッシュ違いのページを個別計測したい」という要件が、標準設定では満たせない。

本資料は、この2つの問題を解消するため、GTMに以下の2点を仕込む手順をまとめたもの。

1. **`#` 以降を含めた完全なパスを返すユーザー定義変数**（カスタムJavaScript）を新設する。
2. **「履歴の変更」トリガー** を用いて、ハッシュ変化時にもタグを発火させる。

これにより、ハッシュルーティング採用サイトでも狙ったページ／セクションでのみタグを発火できる状態を作る。

## 本文構造

### 1. 問題定義 — URLに「#」を含むページとは

`https://abc.com/ddd/viewer?id=123456#/page=1` のような形のURLで、

- `https://abc.com/ddd/viewer?id=123456` ＝ **アンカーリンク前のURL本体**（プロトコル＋ホスト＋パス＋クエリ）
- `#/page=1` ＝ **ハッシュ部分／アンカー部分（フラグメント識別子）**

> アンカーリンク（ページ内リンク）：ページリンクをさらに細かく指定する場合に使用される。アンカーを配置することによりそのページ内の指定位置までリンクすることができる。

典型例として、PDFビューワーや電子書籍ビューワーで「`#/page=1` → `#/page=2` → … → `#/page=6`」とスクロールに応じてハッシュ部分が変動していくサイト（資料中ではマンガビューワーの例で説明）。

### 2. 計測における2つの問題点

| # | 問題 | 影響 |
|---|------|------|
| ① | **URLのハッシュ部分のデータ（`#`以降）はGoogleアナリティクスに送信されない** | ハッシュに重要な情報（ページ番号・セクションID等）があっても、それを計測することができない |
| ② | **ハッシュ部分のみが変化してWebページ内容が書き換わる際は、ページビューイベントが発生しない** | タグの発火設定に通常の「ページビュー」トリガーが利用できない |

### 3. なぜ通常のPage URL指定では動かないか — NG例

【ゴール例】ユーザーがスクロールして `https://abc.com/ddd/viewer?id=123456#/page=6` に到達したタイミングでCVタグを発火させたい。

【素直にやるとこうなる（NG）】

1. GTMでトリガータイプ「ページビュー」を選択
2. 発生場所：「一部のページビュー」
3. 条件：`Page URL` 「含む」 `n/ddd/viewer?id=123456#/page=6`
4. このトリガーをタグに紐づけ

【何が起きるか】

- GTM組み込み変数の `Page URL` には **`#` より前の `https://abc.com/ddd/viewer?id=123456` までしか入らない**。
- かつ、ハッシュ遷移ではページビューイベント自体が起きない。
- 結果、トリガー条件は **「Page URLが `n/ddd/viewer?id=123456` を常に含む」だけ** で評価されてしまう。

> ⇒ ユーザーがサイトのどの位置にいてもタグが発火してしまう状態

つまり、page=1で開いた瞬間にも、page=6到達時にも、区別がつかないまま発火する（または全く発火しない）。

### 4. 解決アプローチ — 2段の手当て

正しいタグ設置は次の2手順をセットで行う。

| 手順 | 何をするか | 解決する問題 |
|------|------------|--------------|
| 手順① | **GTM上で新しい変数を作成し**、GAに送る／トリガー判定に使う「ページ情報」を `#` 込みのものに上書きできるようにする | 問題①（`#` 以降が取得できない） |
| 手順② | 作成した変数を使い、**「履歴の変更」トリガー** でハッシュ部分の変化に対応する発火設定を作る | 問題②（ページビューが起きない） |

→ これでURLに `#` を含むページでもタグの発火を正常にコントロールできるようになる。

### 5. 手順① — 変数の作成（組み込み変数＋ユーザー定義変数の2種）

#### 5-1. (1) 組み込み変数の有効化（GTMに既存のものをONにするだけ）

**操作場所:** GTM管理画面 → 「変数」 > 「組み込み変数」 > 「設定」

**有効化する変数（履歴カテゴリ）:**

| 変数名 | 取得タイミング | 取得元 | 値の中身 |
|--------|----------------|--------|----------|
| **New History Fragment** | 履歴変更トリガーの成立時 | dataLayerの `gtm.newUrlFragment` キー | 履歴変更イベント **後** のページURLのハッシュ部分の文字列 |
| **Old History Fragment** | 履歴変更トリガーの成立時 | dataLayerの `gtm.oldUrlFragment` キー | 履歴変更イベント **前** のページURLのハッシュ部分の文字列 |

→ 2つともチェックを入れて有効化する。これ自体に追加コーディングは不要。

#### 5-2. (2) ユーザー定義変数の新規作成 — `PagePath include hash`

**目的:** Googleアナリティクスに送るページ情報、およびトリガー条件判定に使う「ハッシュ込みのパス」を返す変数を作る。

**操作手順:**

1. GTM →「変数」 >「ユーザー定義変数」 >「新規」をクリック
2. 変数名を **`PagePath include hash`** と入力
3. 変数タイプから **「カスタムJavaScript」** を選択
4. 以下のコードを貼り付けて保存

```javascript
function(){
  return location.pathname + location.search + location.hash;
}
```

> このコードは「現在のURLのパス＋クエリ文字列＋ハッシュ」を結合して返す。`location.hash` が含まれることで `#` 以降も取得できる状態になる。

→ 【手順①】変数の作成完了。

### 6. 手順② — トリガーの設定（履歴の変更トリガー）

**ゴール再掲:** `https://abc.com/ddd/viewer?id=123456#/page=6` に到達した時点でタグを発火させる。

**操作手順:**

1. GTM →「トリガー」 >「新規」
2. トリガータイプから **「履歴の変更」** を選択（その他カテゴリ内）
3. このトリガーの発生場所：**「一部の履歴の変更」** を選ぶ
4. イベント発生時の条件を **2行** 指定する：

| 行 | 変数 | 演算子 | 値 | 役割 |
|----|------|--------|-----|------|
| 1 | `Page URL` | 先頭が一致 | `https://abc.com/ddd/viewer?id=123456` | **ハッシュ前のURL** を限定 |
| 2 | `PagePath include hash` | 含む | `page=6` | **ハッシュ内の特定文字列** を限定 |

→ 「履歴の変更」がトリガー種別なので、ハッシュ遷移が起きるたびに評価が走る。かつ条件で「ハッシュ前のURLが対象ページ」かつ「`#` 以降に `page=6` を含む」を満たした瞬間にのみ発火する。

→ 【手順②】トリガーの設定完了。

ユーザーがページをスクロールして `https://abc.com/ddd/viewer?id=123456#/page=6` に到達した時点で、正常にタグが発火される状態になる。

### 7. 設定チェックリスト（実装時にこの順番で確認）

- [ ] サイトのURL構造を確認し、ハッシュ部分が「セクション遷移／ページ番号／状態」を表しているか把握した
- [ ] GTMの組み込み変数で `New History Fragment` `Old History Fragment` を有効化した
- [ ] ユーザー定義変数 `PagePath include hash`（カスタムJavaScript／`location.pathname + location.search + location.hash` を返す関数）を作成した
- [ ] トリガータイプは「ページビュー」ではなく **「履歴の変更」** を選んでいる
- [ ] トリガー発生場所を「一部の履歴の変更」にし、`Page URL` + `PagePath include hash` の2条件で発火対象を絞っている
- [ ] GTMプレビューモードで、対象URL（例：`#/page=6` 到達時）でのみタグが発火し、それ以外（`#/page=1`～`#/page=5`）では発火しないことを確認した
- [ ] GA側で当該イベント／PVの送信値（Page Pathに `#` 以降が含まれているか）を実データで確認した

### 8. 注意点・落とし穴

- **通常の「ページビュー」トリガーを使い続けると誤発火する**。ハッシュ遷移はページビューを発生させないため、初回ロード時に1回だけ発火する／逆に「Page URL含む」条件が常時マッチして全画面で発火する、といった事故が起こりやすい。
- **`Page URL` 変数では `#` 以降が取れない** ことは仕様。トリガー条件・GA送信値・URL書き換えタグなど、`#` 以降を見たいすべての場所で `PagePath include hash`（ユーザー定義変数）を使う必要がある。
- **「履歴の変更」トリガーはhashchange / pushState / popState すべてに反応する**。SPAでも電子書籍ビューワーでも横展開可能だが、対象を絞らないと過剰発火するため、必ず `Page URL` の先頭一致など追加条件で絞る。
- **GA側のPage Path** にハッシュ込みのデータを送りたい場合は、GAタグの「フィールドを設定する」で `page` フィールドに `{{PagePath include hash}}` を割り当てる運用が前提（資料では明示されていないが、変数名 `PagePath include hash` の命名意図はそれ）。

## 太一視点の示唆 / 次のアクション

### 戦略家としての示唆
- **「CVが取れていない／PVが過剰計測されている」と相談が来た時、URLに `#` があるかを真っ先に確認する** クセをつける。これだけで初動の切り分け時間が大幅に短くなる。
- ハッシュルーティング採用サイトはSPA化の文脈で増え続けている。GTM/GA4の初期診断項目に「Page URLに `#` が混入していないか」を必ず入れる。
- **電子書籍／カタログ／LP内のページ遷移計測は、CV地点だけでなく「途中離脱地点（page=2、page=3…）」も `履歴の変更` トリガーで個別計測できる**。これを起点に「どのページで離脱しているか」のファネル分析→改善提案まで一気に伸ばせる。

### クライアント案件で参照する際の運用手順
1. **診断フェーズ:** 計測したいページ（CV直前・サンクス・LPセクション等）のURLをブラウザで開き、URLに `#` が含まれているかを目視確認。GTMプレビューで `Page URL` 変数の値が `#` 直前で切れていないか確認する。
2. **設計フェーズ:** 上記5-1〜6の手順通りに、組み込み変数有効化 → カスタムJS変数 `PagePath include hash` 作成 → 「履歴の変更」トリガー作成、の3点セットを実装する。
3. **検証フェーズ:** GTMプレビューモードで対象URLを操作し、(a) `PagePath include hash` の値に `#` 以降が入っているか、(b) 狙ったタイミングでのみタグが発火するか、(c) それ以外のタイミングで発火しないか、をチェックリスト（上記7）で確認する。
4. **横展開:** SPA / ハッシュルーティング採用サイトを担当する案件では、初期GTM構築テンプレに `PagePath include hash` 変数と「履歴の変更」用トリガーテンプレを最初から含めておく。毎回の実装コストを下げられる。
