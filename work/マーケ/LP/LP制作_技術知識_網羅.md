### 全体像（LP制作で必要な「技術」の地図）
LP制作の技術は、大きく **「作る（フロント）」「公開する（インフラ）」「計測する（分析）」「守る（運用・セキュリティ）」** に分かれます。受託ではさらに **「納品形態（コード/ツール）」「引き継ぎやすさ」** が重要です。

---

### 1) Webの基礎（ここが土台）
- **Webの仕組み（超ざっくり）**：あなたのLPは「ファイル」ですが、ユーザーには「URLで見えるページ」として届きます。
  - **ブラウザ**：Chrome / Safari など。LPの表示装置
  - **サーバー（ホスティング）**：LPのファイルを置く場所
  - **HTTP/HTTPS**：ブラウザがサーバーに「このURLの中身ちょうだい」と依頼して受け取るルール
  - **URL**：住所（例：`https://example.com/lp`）
  - **キャッシュ**：一度読み込んだものをブラウザやCDNが「貯金」して次を速くする仕組み

- **実務で必須になるキーワード**
  - **DNS**：ドメイン（`example.com`）とサーバーの住所（IPなど）を結びつける電話帳  
    - 受託で揉めやすいポイント：**誰がどのアカウントでドメインを管理しているか**（ムームー/お名前.com/Cloudflare等）
  - **ステージング（仮公開）**：本番の前に関係者が確認できるURL
  - **本番（プロダクション）**：ユーザーが見るURL
  - **リダイレクト**：URLの転送（`http`→`https`、`www`あり/なし統一など）
  - **同一生成物・環境差**：同じファイルでも、設定やタグで挙動が変わる（計測タグ、Cookie同意など）

- **LPの“3大要素”と、どこまでやれば受託で勝てるか**
  - **HTML（骨組み）**：見出し/文章/CTA/フォームなど「情報の意味」を決める。**SEO/アクセシビリティ/計測の土台**
  - **CSS（見た目）**：レイアウト・余白・タイポグラフィ。**CVに効くのは“読みやすさ”と“押しやすさ”**
  - **JavaScript（動き）**：最低限でOK。FAQ、スムーススクロール、フォームの軽い制御、計測イベントが中心

- **レスポンシブの現実（初心者が最初に知るべきこと）**
  - LPは **8割以上スマホで見られる** 前提になりやすい（案件により差はある）
  - 重要なのは「画面幅」だけでなく、**指で押せるサイズ**、**読みやすい行間**、**スクロールで迷子にならない構造**

- **最初の要件確認（これができると“技術者っぽい”）**
  - **公開先**：どこに置く？（既存サイト配下 / サブドメイン / 独自ドメイン新規）
  - **フォーム送信先**：メール？スプレッドシート？CRM？
  - **計測**：GTM/GA4/広告CVは必須？イベントは何を見る？
  - **更新運用**：誰が・どの頻度で・何を更新する？（文言だけ？画像も？セクション追加も？）

#### 受託でよくあるトラブル（原因が“Webの基礎”にあるやつ）
- **「DNS変えたのに反映されない」**：DNSは反映に時間がかかることがある（数分〜最大で丸1日見込む）
- **「更新したのに古い表示」**：ブラウザ/CDNキャッシュが残っている（シークレットで確認、キャッシュ設定確認）
- **「httpsなのに警告が出る」**：混在コンテンツ（httpの画像/スクリプトを読んでいる）
- **「wwwあり/なしで表示が違う」**：リダイレクト・正規URLの統一ができていない（SEO/計測が割れる）

### 2) HTML（LPの構造を作る）
- **セマンティックHTML（＝意味のある骨組み）**：見た目ではなく「この塊は何か」をタグで表します。これができると、SEO/アクセシビリティ/計測が一気に楽になります。
  - 例：`header`（上部）/ `main`（主内容）/ `section`（まとまり）/ `footer`（下部）/ `nav`（導線）

- **LPでよくある“定番セクション”とHTMLの考え方**
  - **FV（ファーストビュー）**：`h1`（最重要の見出し）＋補足文＋CTAボタン
  - **ベネフィット**：箇条書き（`ul`/`li`）が読みやすい
  - **実績/お客様の声**：カード型の繰り返し構造（同じHTMLを繰り返す）
  - **料金/プラン**：表（`table`）よりカードの方がスマホで崩れにくいことが多い
  - **FAQ**：後でアコーディオンにするなら、質問と回答のまとまりを意識して作る
  - **最終CTA**：フォーム or 予約/問い合わせ導線（必ず“押す先”を明確に）

- **見出し設計（受託で品質が出るポイント）**
  - **h1は原則1つ**（ページの看板）
  - 以降は **h2 → h3** の順で「章立て」する（見出しレベル飛びは避ける）
  - 見出しは“装飾”ではなく“構造”。装飾はCSSでやる

- **フォーム（最重要。ここが壊れるとLPが死ぬ）**
  - **最低限の要素**：氏名/会社名/メール/電話/問い合わせ内容…など（案件次第）
  - **必須・任意**：ユーザーが迷わない表示（`required` の有無、必須マーク）
  - **エラー表示**：何がダメで、どう直せばいいか（「入力してください」だけだと弱い）
  - **送信後**：完了画面（サンクス） or 同一ページ内完了表示（計測の設計にも直結）
  - **二重送信**：送信ボタン連打の対策が必要（JS/フォームサービス側で対応）

- **OGP/メタ情報（“SNSで崩れない”）**
  - **title**：検索結果やタブ名になる（最重要）
  - **description**：検索結果の説明文（100〜120文字くらいを目安に要約）
  - **OGP**：SNS共有時のサムネ/タイトル/説明の表示
  - 受託で確認すること：**OGP画像のサイズ（推奨比率）** と **文言の最終版**

- **画像の扱い（表示速度にも直結）**
  - **alt（代替テキスト）**：画像が読めない時に何が書いてあるか伝える
  - **幅・高さ指定**：レイアウトがガタつく（CLS）を防ぐ
  - **“文字入り画像”の罠**：スマホで潰れる。可能ならテキスト化してCSSで組む

- **実務チェックリスト（HTML編）**
  - **リンク切れ**（電話/メール/外部リンク含む）がない
  - **CTAの押し先**が全CTAで一致している（フォーム/LINE/予約など）
  - **フォームの必須条件**が要件どおり
  - **サンクス**のURL/表示が用意されている（計測できる）

#### 最小のHTML雛形（静的LPの“型”）
```html
<!doctype html>
<html lang="ja">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />

    <title>（LPタイトル）</title>
    <meta name="description" content="（100〜120文字の要約）" />

    <!-- OGP（最低限） -->
    <meta property="og:title" content="（OGPタイトル）" />
    <meta property="og:description" content="（OGP説明）" />
    <meta property="og:type" content="website" />
    <meta property="og:url" content="https://example.com/lp" />
    <meta property="og:image" content="https://example.com/ogp.jpg" />

    <link rel="icon" href="/favicon.ico" />
    <link rel="stylesheet" href="/styles.css" />
  </head>
  <body>
    <header>
      <nav aria-label="サイト内ナビゲーション">
        <!-- ロゴや導線 -->
      </nav>
    </header>

    <main id="top">
      <section aria-label="ファーストビュー">
        <h1>（一番伝えたい価値）</h1>
        <p>（補足。誰の何をどう解決するか）</p>
        <a href="#form" class="btn">無料で相談する</a>
      </section>

      <section>
        <h2>選ばれる理由</h2>
        <ul>
          <li>理由1</li>
          <li>理由2</li>
          <li>理由3</li>
        </ul>
      </section>

      <section id="faq">
        <h2>よくある質問</h2>
        <!-- アコーディオンにする場合でも、HTMLはまず“質問と回答の塊”を作る -->
        <div class="faq-item">
          <button type="button" class="faq-q" aria-expanded="false">
            Q. 〜ですか？
          </button>
          <div class="faq-a" hidden>
            <p>A. 〜です。</p>
          </div>
        </div>
      </section>

      <section id="form" aria-label="お問い合わせフォーム">
        <h2>お問い合わせ</h2>
        <form>
          <label>
            お名前（必須）
            <input name="name" autocomplete="name" required />
          </label>
          <label>
            メール（必須）
            <input type="email" name="email" autocomplete="email" required />
          </label>
          <button type="submit" class="btn">送信する</button>
        </form>
      </section>
    </main>

    <footer>
      <small>© （会社名）</small>
    </footer>

    <script src="/main.js" defer></script>
  </body>
</html>
```

#### HTMLの“現場ルール”（これだけ守ると強い）
- **CTAはアンカーで飛べる**ようにする（例：`href="#form"`）→計測もしやすい
- **ボタンとリンクを使い分ける**：ページ移動は`a`、操作は`button`
- **フォームはautocompleteを入れる**：入力が速くなり、離脱を減らしやすい

### 3) CSS（見た目・レイアウト・スマホ最適化）
- **CSSの基本（ここだけは外せない）**
  - **ボックスモデル**：要素は「中身 + 余白」でできている  
    - `padding`（内側）/ `margin`（外側）/ `border`（枠）
  - **カスケード（優先順位）**：後に書いたもの、より具体的な指定が勝つ  
    - 受託で困る典型：修正したのに反映されない → **優先順位の衝突**
  - **レスポンシブの前提**：スマホが基準（Mobile First）だと設計がラク

- **LPで頻出のレイアウトパターン（まずはこれだけ作れればOK）**
  - **2カラム**（画像＋テキスト、左右入れ替え）：Flexboxで対応
  - **カードの横並び→スマホで縦**：Flexbox + `flex-wrap` / もしくはGrid
  - **中央寄せ＋最大幅**：`max-width` と `margin: 0 auto`
  - **セクションの余白統一**：上下 `padding` をルール化する

- **レスポンシブ設計の実務ルール（迷わないための型）**
  - **ブレイクポイント**：まずは 1〜2個で十分（例：スマホ / それ以外）
  - **文字**：スマホで小さすぎない（読みやすさ優先）
  - **ボタン**：指で押せる高さ・余白を確保（小さいCTAはCVを落としやすい）
  - **行の長さ**：PCで横に長すぎると読みにくい → コンテナ幅を制限

- **タイポグラフィ（“それっぽさ”が一気に出る）**
  - **フォントサイズ**：本文・見出し・注釈に階層を作る
  - **行間（line-height）**：詰まりすぎると読む気が失せる
  - **字間（letter-spacing）**：日本語は基本いじりすぎない

- **色・余白・角丸（デザインの統一）**
  - **色は増やしすぎない**（メイン/サブ/アクセント/グレー）
  - **余白の単位**を揃える（例：8px刻み）
  - **ボタンの状態**：hover/active/focus を最低限入れる（特にfocusはアクセシビリティ）

- **アニメーション（やるなら目的を決める）**
  - 目的例：**押せる感**（hover）/ **セクションの注目**（ふわっと表示）
  - 注意：多用すると重くなる。**まずは計測してから強化**

- **実務チェックリスト（CSS編）**
  - スマホで **横スクロールが発生していない**
  - 画像やカードが **はみ出していない**
  - フォントと余白が **セクションごとにバラバラになっていない**
  - CTAボタンが **小さすぎない／押しにくくない**

#### 最小のCSS土台（まずこれを作ると速い）
```css
/* まずは崩れを減らす */
*,
*::before,
*::after {
  box-sizing: border-box;
}

body {
  margin: 0;
  font-family: system-ui, -apple-system, "Hiragino Kaku Gothic ProN", "Noto Sans JP", sans-serif;
  line-height: 1.7;
  color: #111;
}

img {
  max-width: 100%;
  height: auto;
  display: block;
}

.container {
  width: min(100% - 32px, 1000px);
  margin: 0 auto;
}

.btn {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  min-height: 48px; /* 指で押しやすい最低ライン */
  padding: 0 16px;
  border-radius: 12px;
  background: #2563eb;
  color: #fff;
  text-decoration: none;
  font-weight: 700;
}
.btn:focus-visible {
  outline: 3px solid #93c5fd;
  outline-offset: 2px;
}

@media (min-width: 768px) {
  .btn {
    min-height: 52px;
    padding: 0 18px;
  }
}
```

#### CSSで“速く作る”コツ（受託向け）
- まず **コンテナ幅** と **セクション余白** を固定ルールにする（全体が揃う）
- 色は **3〜4色**（本文/見出し/アクセント/薄いグレー）に抑える
- 「デザインっぽさ」は **余白と行間** で出す（派手な装飾より効く）

### 4) JavaScript（最低限でOK：LPに必要な“ちょい動き”）
- **結論：LPのJSは“少なくて強い”が正解**
  - LPは基本「読ませて、押してもらう」ページ。JSを盛りすぎると **遅くなる・バグる・計測が壊れる** リスクが増えます。

- **最低限おさえる概念**
  - **DOM**：HTML要素をJSから操作する対象
  - **イベント**：クリック、スクロール、入力など
  - **状態（state）**：開いてる/閉じてる、送信中/送信完了など

- **LPでよく使う機能（実務での使い所）**
  - **FAQアコーディオン**：長文を畳んで読みやすくする
  - **スムーススクロール**：目次やCTAからフォームに飛ばす（やりすぎると酔う人もいる）
  - **固定CTA（追従ボタン）**：スマホで特に強い。押しやすさを上げる
  - **モーダル**：規約表示や画像拡大など（フォーム前に邪魔しない設計が重要）

- **フォーム制御（“壊れない”が最優先）**
  - **二重送信防止**：送信中はボタンを無効化して文言を変える
  - **簡易バリデーション**：メール形式、必須、文字数（ただし最終的な検証は送信先でも必要）
  - **完了時の処理**：サンクス表示、計測イベント送信、リダイレクト

- **計測イベント（LPのJSで一番価値が出る場所）**
  - **クリック**：CTAクリック、電話/LINEクリック、資料DLクリック
  - **フォーム**：送信ボタン押下、送信成功（最重要）
  - **到達**：特定セクションまでスクロールしたか（任意）
  - 重要：**“押した”と“送信成功”は別**。CVは基本「成功」で取る

- **落とし穴（初心者がやりがち）**
  - **読み込み順問題**：HTMLより先にJSが動いて要素が見つからない
  - **他タグとの競合**：GTMや広告タグが同じイベントを二重に拾う
  - **スマホSafari差**：スクロール固定、`position: sticky`、タップ判定などで差が出ることがある
  - **重いライブラリ**：小さいLPに大きいライブラリを入れると速度が落ちる

- **実務チェックリスト（JS編）**
  - FAQ/メニュー/モーダルが **スマホで必ず動く**
  - フォームが **送信できる／二重送信しない**
  - 計測イベントが **重複していない**（同じクリックで2回飛ばない）

#### よく使う最小スニペット（まずは“動く”を優先）
**FAQアコーディオン（最小）**
```js
document.querySelectorAll(".faq-item").forEach((item) => {
  const q = item.querySelector(".faq-q");
  const a = item.querySelector(".faq-a");
  if (!q || !a) return;

  q.addEventListener("click", () => {
    const isOpen = q.getAttribute("aria-expanded") === "true";
    q.setAttribute("aria-expanded", String(!isOpen));
    a.hidden = isOpen;
  });
});
```

**フォーム二重送信防止（最小）**
```js
const form = document.querySelector("form");
const submitBtn = form?.querySelector('button[type="submit"]');

form?.addEventListener("submit", () => {
  if (!submitBtn) return;
  submitBtn.disabled = true;
  submitBtn.textContent = "送信中…";
});
```

### 5) 制作の選択肢（受託で最重要：どの納品形態にするか）
- **ここを間違えると“作れるのに儲からない/揉める”**ので、最初に決めます。

- **納品形態の代表例（初心者向けの現実解つき）**
  - **ノーコード（STUDIO/Webflow等）**
    - **向いてる**：スピード重視、更新をクライアントが自分でやりたい
    - **強み**：爆速、運用しやすい、見た目が揃いやすい
    - **注意**：月額費用、計測の自由度、フォーム連携、データの持ち出し（引き継ぎ）
  - **WordPress**
    - **向いてる**：既存サイトがWP、更新が多い、ブログ/固定ページ運用
    - **注意**：テーマ/プラグイン依存、表示速度、セキュリティ/更新管理
  - **静的HTML（HTML/CSS/JS）**
    - **向いてる**：広告LP、ページ数少なめ、要件がシンプル、速度重視
    - **強み**：構成が単純で壊れにくい、速い、どこでも置ける
    - **注意**：更新は“ファイル編集”になりがち（運用方法を決めないと詰む）
  - **React/Next.js等（モダン）**
    - **向いてる**：複雑なUI、会員/ログイン、他システムと深い連携、ABテスト基盤
    - **注意**：構築・運用コストが上がる。初心者は“過剰設計”になりやすい

- **案件での決め方（質問テンプレ）**
  - **更新頻度**：月に何回？誰が更新？（担当者のスキルも聞く）
  - **フォーム要件**：メールだけ？CRM連携？スパム対策要件は？
  - **計測要件**：GTMは必須？広告媒体は？同意管理は必要？
  - **公開先**：既存ドメイン配下？新規ドメイン？サブドメイン？
  - **納期**：急ぎならノーコード/静的に寄せるのが現実的

- **“納品物”を明確にする（受託の技術要件）**
  - **編集権限**：誰がどのアカウントで管理するか
  - **ソースの引き渡し**：Git/Zip/ビルダーの共有、どれで渡すか
  - **運用手順書**：文言修正の場所、画像差し替え、計測タグの触り方
  - **保守範囲**：公開後の軽微修正は何回まで含むか（技術というより事故防止）

#### 初心者が受託で失敗しにくい“選び方”（迷ったらこれ）
- **広告LP（更新少）**：静的HTML +（Netlify/Vercel等）→ 速い・壊れにくい
- **クライアントが頻繁に更新**：STUDIO/Webflow等 → 運用が回る
- **既存サイトがWordPress**：WP固定ページで作る → 管理が一元化できる

#### 見積もりに効く「技術要件の書き方」例（そのまま使えます）
- **公開環境**：ステージングURL + 本番URL、HTTPS化、www統一
- **対応デバイス**：スマホ（iPhone Safari）/ PC（Chrome）での表示確認を含む
- **フォーム**：テスト送信確認、二重送信対策、サンクス表示
- **計測**：GTM導入（もしくは既存利用）、CTAクリック/送信成功のイベント計測

### 6) 公開（インフラ）：ドメイン・サーバー・デプロイ
- **公開は“作る”のと同じくらい重要**です。ここで詰まると納期に直撃します。

- **公開の基本フロー（まずはこの型で回す）**
  - **(1) ローカルで確認**：自分のPCで表示が崩れてないか確認
  - **(2) ステージングに仮公開**：関係者レビュー用URLを出す
  - **(3) 本番公開**：ドメインをつなぎ、一般ユーザーが見られる状態にする
  - **(4) 公開後確認**：表示、フォーム、計測、速度を最終チェック

- **ドメインとDNS（受託で絶対に聞く）**
  - **ドメインは誰の所有か**：クライアントが持つのが原則（代理取得はリスク）
  - **DNSの編集権限があるか**：A/CNAMEレコードを触れないと公開できない
  - **wwwあり/なし**・**http→https** の統一方針（SEO/計測の整合性にも影響）

- **ホスティングの選び方（初心者向けの現実解）**
  - **静的LP**：Netlify / Vercel / Cloudflare Pages が相性良いことが多い
    - **メリット**：HTTPSが楽、デプロイが簡単、戻せる（ロールバック）運用がしやすい
  - **既存サイト配下**：レンタルサーバーやCMSに載せることも多い
    - **注意**：環境依存（PHP/WordPressの制約）、キャッシュで更新が反映されにくいことがある

- **HTTPS（SSL）の落とし穴**
  - HTTPS化はほぼ必須（フォームや広告でも問題になりやすい）
  - まれに **混在コンテンツ**（httpsページ内でhttp画像を読んで警告）が出る → 画像/外部読み込みを確認

- **キャッシュ（更新したのに見えない問題）**
  - CDN/ブラウザのキャッシュで「古い表示」が残ることがある
  - 対策：ファイル名変更（画像差し替え時）、キャッシュクリア、デプロイ設定確認

- **公開後の“必須”確認項目（ここまでが納品）**
  - **スマホ実機（iPhone Safari）**で崩れがない
  - **フォーム送信**が成功し、送信先に届く（テスト送信）
  - **サンクス**が表示される（または完了メッセージ）
  - **GTM/GA4/広告CV**が想定どおり発火する（重複していない）
  - **404がない**（リンク、画像、ファイル）
  - **速度**：画像が重すぎて初回表示が遅くない

#### DNS設定でよく出るレコード（言葉だけ知っておけばOK）
- **Aレコード**：ドメイン → サーバーIP（例：`example.com` をどこに向けるか）
- **CNAME**：サブドメイン → 別名（例：`www.example.com` を `example.com` に寄せる等）
- **TXT**：所有確認など（Google/Meta、SSL、ドメイン認証で出がち）

#### 公開時に“最低限”やると事故が減ること
- **ステージングで関係者確認 → OK後に本番DNS切り替え**（いきなり本番は危険）
- 本番切り替え後、**シークレットウィンドウ**で表示確認（キャッシュの影響を受けにくい）
- **サンクス到達**までを“納品テスト”に含める（フォームは途中で落ちやすい）

### 7) フォーム（LPの心臓）：送信先の設計
- **送信先の種類**
  - **メール**（フォーム→メール通知）
  - **スプレッドシート**（Google Forms/Apps Script等）
  - **CRM/MA**（HubSpot、Salesforce、Marketo等）
- **スパム対策**：reCAPTCHA、ハニーポット、レート制限（サービス側で対応することも多い）
- **完了ページ/完了イベント**：CV計測に直結（「送信したつもり」対策）

---

### 8) 計測（マーケ目的のLPに必須）
- **Google Tag Manager（GTM）**：タグを安全に管理する箱
- **GA4**：PVだけでなくイベント（クリック/送信/到達）で見る
- **広告計測**：Meta/Google/Yahoo等のピクセル、コンバージョン設定
- **UTM**：流入元を識別するパラメータ
- **重複計測/欠損**：同じイベントが2回飛ぶ、iOS/ブラウザ制限で欠損、同意管理の影響

---

### 9) SEO（“検索流入も狙うLP”なら）
- **基本**：title/description、見出し構造、内部リンク、正規URL（canonical）
- **構造化データ**：FAQ等（必要時）
- **インデックス**：noindex、サイトマップ（ケースによる）
- **画像最適化**：ファイル形式、遅延読み込み、サイズ指定（SEOというより速度）

---

### 10) 表示速度・品質（CVに効く“地味に重要”）
- **Core Web Vitals**：LCP/CLS/INPの考え方
- **画像最適化**：WebP/AVIF、圧縮、適正サイズ、`srcset`
- **読み込み**：遅延読み込み、不要JS削減、フォント最適化
- **クロスブラウザ**：Chrome/Safari（特にiPhone）で確認

---

### 11) アクセシビリティ（最低ラインは押さえる）
- **キーボード操作**：フォーカスが移動できる
- **コントラスト**：薄すぎる文字はNG
- **代替テキスト**：画像の意味が伝わる
- **フォーム**：ラベル、エラー表示が分かる

---

### 12) セキュリティ・法務まわり（受託で揉めやすい）
- **個人情報**：フォームで何を取得するか、保管先、閲覧権限
- **Cookie/同意**：計測タグを同意後に発火させる必要がある場合（業種・地域で要件増）
- **脆弱性の基本**：XSS/CSRFの概念（フォームや外部埋め込みで意識）
- **素材の権利**：画像・フォント・文章のライセンス（制作事故防止）

---

### 13) 制作のためのツール基礎（作業効率＝利益）
- **エディタ**：VS Codeの基本（拡張、整形、検索）
- **ブラウザ開発者ツール**：検証、レスポンシブ、ネットワーク（遅い原因を見る）
- **デザイン受け渡し**：Figmaの見方（余白、色、書き出し）
- **画像編集/圧縮**：サイズ調整・圧縮の手順

---

### 14) 受託で“技術として”必要な進め方（納品事故を防ぐ）
- **要件定義**：目的（CV定義）、計測内容、フォーム項目、公開場所、運用者
- **環境分け**：テストURL（仮公開）→本番公開
- **チェックリスト**：スマホ表示、リンク、フォーム、計測、速度、誤字、規約/プライバシー
- **引き継ぎ**：更新方法（どこを触れば文言が変わるか）、アカウント管理、バックアップ

### 15) 初心者におすすめの学習順（最短で受託に到達）
